# OBoard Agent Protocol

This document defines the wire contract between OBoard Controller and OBoard Agent. It is intentionally written as a developer document because the panel UI should not expose these internal details to normal users.

## Scope

The Agent protocol covers:

- Agent enrollment.
- Agent-authenticated HTTP callbacks.
- Controller-to-Agent WebSocket task delivery.
- Task payload and result contracts.
- Install/update script endpoints used by the Agent.

The protocol boundary is JSON over HTTP/WebSocket. Controller and Agent do not depend on each other's Go `internal` packages after repository separation; matching JSON fields define the current wire contract and are updated together.

All paths below are relative to the Controller base URL. If the Controller uses
`OBOARD_BASE_PATH=/hidden`, the Agent `controller_url` is
`https://panel.example.com/hidden`; enrollment, WebSocket, callbacks, install
scripts, downloads, and health checks then remain under that prefix. The
Controller does not expose unprefixed Agent endpoints while a base path is set.
When an administrator changes the path online, Controller temporarily accepts
both the previous and current prefixes. It sends every enrolled Agent an
`update_agent_config` patch containing the complete new `controller_url` and
removes the previous prefix only after all target Agents report success.

## Versions

Controller exposes expected Agent/Core versions at:

```http
GET /api/v1/version
```

Important response fields:

```json
{
  "agent_expected_version": "0.1.0-dev",
  "agent_expected_build": "20260708005400",
  "agent_update_repo": "obrdx/oboard-agent",
  "kernel_version": "0.1.0-dev",
  "kernel_build": "20260708005400"
}
```

The build number is used for current capability gates and update decisions. Controller does not translate new tasks for older Agent contracts; incompatible Agents must be updated before receiving those tasks.

## Authentication

Agent-authenticated endpoints require both headers:

```http
X-Agent-ID: <agent_id>
Authorization: Bearer <agent_token>
```

Controller stores only `HashSecret(agent_token)`. Requests are accepted when `X-Agent-ID` resolves to a server and the bearer token hash matches that server's stored token hash.

The Agent is a root-equivalent host-management boundary. A Controller role that
can enqueue configuration, tunnel, forwarding, service or update tasks can cause
privileged changes on enrolled nodes. Protect Operator/Admin sessions, Agent
tokens and the release-signing key accordingly; do not treat an enrolled Agent
as a low-privilege telemetry daemon.

installation. It defaults to false and is persisted with the Agent config. The
controller sends the *effective* value (server flag AND the global
`audit_enabled` and `connection_audit_enabled` settings) in enrollment and
every hello/heartbeat, so disabling the audit console or the global
connection-audit gate stops every Agent from collecting, clears its local
audit state file, and halts reporting without a task.

## WebSocket Channel

### `GET /api/v1/agent/connect`

The Agent converts `controller_url` to WebSocket scheme:

- `http://host[/base]` -> `ws://host[/base]/api/v1/agent/connect`
- `https://host[/base]` -> `wss://host[/base]/api/v1/agent/connect`

Auth headers are required.

### Connection Flow

1. Controller accepts the WebSocket and sends `hello`.
2. Agent sends a `health_report` immediately.
3. `hello` and every `heartbeat` carry the current latency test plan. Agent
   applies its persistent version gate before replacing the local plan.
4. Controller either sends a `task_request` when a pending task exists, or sends
   `heartbeat` according to the current monitoring policy.
5. Agent executes one task at a time, posts the result and current health
   snapshot over HTTP, then sends a small `task_ack` on the socket. While
   connection audit is enabled it also sends independent `presence_delta`
   messages on this socket.
6. The scheduled latency and metric loops belong to the Agent process, not the
   WebSocket. They continue while Controller is unreachable and queue reports
   for acknowledged replay. Metric samples are captured every 60 seconds.
7. Controller acknowledges a committed or equivalent historical metric sample
   with `metric_report_ack`; Agent then advances its durable queue immediately.
8. If a connection drops while a task is in-flight, Controller requeues that
   task as pending with a readable result message.

### Reconnect

Agent reconnect jitter is local and does not change the WebSocket or task
contract. The process still connects immediately on first start.

- After a session of at least 60 seconds, the first reconnect waits
  `SHA-256(agent_id + NUL + controller_url)` modulo 5000 milliseconds so a
  Controller restart does not reconnect the whole fleet at once.
- Consecutive failures use full jitter: attempt 0 waits 0–1s, then 0–2s, 0–4s,
  up to 0–60s.
- HTTP 401/403 or identity failures wait 2–5 minutes.
- `update_agent` payload, task signing, Agent ID/token, and `task_ack` are
  unchanged.

```json
{
  "type": "hello",

  "server_id": 3,
  "connection_audit_enabled": false,
  "latency_probe_plan": {
    "version": 1783278569000,
    "resource_version": "0e17b69211fc4226",
    "mode": "tcp",
    "enabled": true,
    "interval_seconds": 60,
    "sample_count": 3,
    "interval_ms": 150,
    "timeout_ms": 3000,
    "targets": [{"probe_id":"public-cloudflare","kind":"public","host":"cp.cloudflare.com","port":443}]
  }
}
```

`heartbeat`:

```json
{
  "type": "heartbeat",
  "ts": "2026-08-13T00:00:20Z",
  "connection_audit_enabled": false,
  "desired_config_revision": 42,
  "configuration_sync_state": "queued",
  "configuration_sync_version": 17,
  "latency_probe_plan": {"version":1783278569000,"resource_version":"0e17b69211fc4226","mode":"tcp","enabled":true,"interval_seconds":60,"sample_count":3,"interval_ms":150,"timeout_ms":3000,"targets":[{"probe_id":"public-cloudflare","kind":"public","host":"cp.cloudflare.com","port":443}]}

```

Both messages carry the Controller's current effective server audit setting.
`desired_config_revision`, `configuration_sync_state`, and
`configuration_sync_version` are Controller-to-Agent convergence hints. They
contain no configuration or secret material. The Agent does not treat a hint as
an authorization or a task; the signed task queue remains the only execution
path. Controller compares the Agent's authenticated health report with this
state and re-wakes/rebuilds the durable task when a notification was lost.
This keeps an Agent that was offline during a settings change synchronized on
its next connection without a retrying task. The cross-project contract test
`TestControllerAndAgentProcessesConvergeOfflineSavedConfiguration` builds and
launches real Controller and Agent binaries as separate OS processes. It saves
configuration while Agent is offline, reconnects the enrolled Agent, verifies
the signed deployment executes and reports applied metadata, and waits for the
real Controller sync row to become `synced`. The narrower
`TestAgentSubprocessExecutesDeploymentAndReportsAppliedMetadata` also launches
the Agent test binary as a separate OS process and runs the real `Runner.connect`: it verifies signature v2, executes an `apply_deployment`,
posts the authenticated result with matching `applied_config_version` and
payload digest, then acknowledges the task over WebSocket. The Agent persists a changed value
and applies it to the local core API; disabling clears local pending audit
state and disables the core aggregation maps. The latency plan uses the same
persistent-version rule as other desired state: an older version is rejected,
an identical same-version plan is idempotent, and different content under the
same version is rejected.

`latency_probe_report` is Agent-to-Controller and is independent of task
results. Agent sends the oldest unacknowledged report first and retries it no
more often than every 10 seconds until Controller returns
`latency_probe_ack`:

```json
{
  "type": "latency_probe_report",
  "latency_probe_report": {
    "report_id": "agent-a-latency-1783278629000000000-7",
    "resource_version": "0e17b69211fc4226",
    "checked_at": "2026-08-13T00:10:29Z",
    "items": [{
      "probe_id": "public-cloudflare",
      "kind": "public",
      "mode": "tcp",
      "host": "cp.cloudflare.com",
      "ip": "",
      "port": 443,
      "available": true,
      "latency_ms": 24,
      "min_latency_ms": 19,
      "p95_latency_ms": 31,
      "jitter_ms": 5,
      "sample_count": 3,
      "success_count": 3,
      "checked_at": "2026-08-13T00:10:29Z"
    }]
  }
}
```

```json
{"type":"latency_probe_ack","report_id":"agent-a-latency-1783278629000000000-7","ts":"2026-08-13T00:10:35Z"}
```

Agent stores the plan, last-run time, and up to 2,048 pending reports in
`state_dir/latency-probe.json` with mode `0600`. Pending reports older than 35
days are discarded. Controller accepts observations within that replay window,
deduplicates `report_id` plus `probe_id`, and stores the Agent logical-clock
observation time instead of the reconnect time.

`presence_delta` is Agent-to-Controller and shares the WebSocket with
`task_ack`; it is not a task response:

```json
{
  "type": "presence_delta",
  "presence_delta": {
    "dropped_count": 0,
    "events": [{
      "seq": 9821,
      "server_id": 3,
      "user_id": 7,
      "inbound_id": 4,
      "path_id": 17,
      "device_id_hash": "controller-hmac",
      "credential_epoch": 2,
      "source_ip": "198.51.100.20",
      "network": "tcp",
      "event": "first_meaningful_payload",
      "state": "active",
      "active_connections": 1,
      "meaningful": true,
      "payload_last_at": "2026-08-07T01:02:03Z",
      "at": "2026-08-07T01:02:03Z"
    }]
  }
}
```

Agent polls kernel and Agent-native SSH presence once per second, assigns one
monotonic sequence across both sources, and bounds each delta to 500 events. A
poll that drains more than one delta's worth is written as several messages in
sequence order, so a backlog accumulated while Agent was offline never becomes a
frame larger than the Controller websocket read limit. Events a closed
connection did not accept keep their sequence and are retried on the next
connection, bounded to 4,096 buffered events; events older than five minutes are
dropped locally and counted in `dropped_count` instead of failing a later batch
against the Controller acceptance window.
Events are `first_authenticated`, `first_meaningful_payload`,
`activity_refresh`, `last_connection_closed`, and `credential_rejected`.
Controller applies `(agent_id, seq)` idempotently, validates accounting
location and current device epoch, and derives `route_id` from its signed
offline GeoIP data. TCP presence expires after 120 seconds and UDP after 60
seconds; confirmed probes contribute no online-device presence.

`task_request`:

```json
{
  "type": "task_request",
  "ts": "2026-07-08T00:00:00Z",
  "task": {
    "id": 79,
    "server_id": 3,
    "type": "apply_deployment",
    "payload_json": "{\"version\":1783278569,\"config\":{\"config\":\"...\"},\"config_changed\":true,...}",
    "status": "running",
    "result_json": "{}",
    "config_version": 1783278569,
    "nonce": "EsTG3vTznJ6ACPL3",
    "created_at": "2026-07-08T00:00:00Z",
    "updated_at": "2026-07-08T00:00:00Z"
  },
  "signature": "base64url-hmac"
}
```

Task signature version 2 is computed over task ID, `server_id`, task type,
`config_version`, nonce and `payload_json` using the stored Agent token hash.
The Agent rejects older signature versions, verifies the HMAC before execution,
and then checks that the signed `server_id` matches its enrolled identity.

Every Controller `hello`, `heartbeat`, and `task_request` carries its current
UTC time in `ts`. Agent retains this as a short-lived reference for time checks;
it is not part of the signed task envelope and is never applied directly to the
host clock.

For configuration and deployment tasks, the Agent persists the last successful
`config_version` and a payload digest. Older versions are rejected across
restarts; an identical same-version replay is a no-op, while different content
under an already-applied version is rejected.

`config_version` is an opaque positive `int64`, not a Unix-seconds timestamp.
Controller allocates it from one durable monotonic sequence shared by
`apply_deployment` and `apply_core_config`, with the current Unix millisecond
value and existing task versions used only as lower bounds. All tasks belonging
to one multi-server deployment carry the same allocated version.

### Agent Messages

`health_report`:

```json
{
  "type": "health_report",
  "health_report": {
    "status": "online",
    "public_ipv4": "203.0.113.10",
    "public_ipv6": "2001:db8::10",
    "interface_ipv6": "2400:3200::10",
    "region_code": "HK",
    "os": "linux",
    "arch": "amd64",
    "agent_version": "0.1.0-dev",
    "agent_build": "20260708005400",
    "sing_box_version": "oboard-sb 0.1.0-dev",
    "kernel_capabilities": ["family_selector_v1", "connection_presence_v1"],
    "applied_config_version": 17,
    "applied_config_digest": "sha256-of-last-applied-task-payload"
  }
}
```

Health reports are best-effort. `region_code` is the upper-case two-letter region detected from the Agent's own exit network and is refreshed with the public-IP probe. `public_ipv4`/`public_ipv6` come from outbound probes of the Agent's exit network. `interface_ipv6` is a local, network-free scan of global IPv6 addresses assigned to interfaces; it reports inbound IPv6 capability for hosts whose IPv6 is inbound-only, and Controller uses it for listener binding and as the IPv6 entry-address fallback only (never for egress IP-stack decisions). `kernel_capabilities` is the sorted, unique, bounded capability list parsed from `oboard-sb version` JSON (at most 64 entries and 128 bytes per entry); Controller stores it as runtime metadata and refuses desired state requiring an absent capability rather than sending unsupported kernel JSON. `applied_config_version` and `applied_config_digest` are local persistent version metadata only; they never contain configuration, credentials, or task payloads. Controller uses them to detect local drift or a lost task notification. Missing optional fields must not fail enrollment or heartbeat handling.

`cpu` is the host CPU model string from `/proc/cpuinfo` (`model name` or `Hardware`). `cpu_cores` is the logical CPU count from `processor` lines, with `runtime.NumCPU()` as fallback. The two fields are independent: never parse a core count out of the model name. Omitting `cpu_cores` or sending `0` keeps the last known Controller value.

`host_uptime_seconds` is the time since the host last booted (`/proc/uptime` on Linux, `DurationSinceBoot` on Windows; omitted elsewhere). It is a monotonic duration, so Controller derives `host_booted_at` on its own clock and a skewed or corrected node clock never moves it. Controller keeps the previous boot time while the derived value stays within two minutes, so report latency does not churn it, and resets it after a reboot. Omitting it or sending `0` keeps the last known value.

`metric_report` carries historical resource samples only and never updates live
server state, `last_seen_at`, traffic baselines, or SLA state:

```json
{
  "type": "metric_report",
  "metric_report": {
    "report_id": "9fb4e53e8d934b8c88af870266f305c1",
    "sampled_at": "2026-08-23T12:34:17.123Z",
    "cpu_usage_percent": 18.5,
    "memory_used_bytes": 1073741824,
    "memory_total_bytes": 4294967296,
    "disk_used_bytes": 21474836480,
    "disk_total_bytes": 107374182400,
    "tcp_connection_count": 81,
    "udp_connection_count": 12,
    "process_count": 146,
    "network_upload_bps": 12000,
    "network_download_bps": 42000
  }
}
```

Controller preserves the original `sampled_at` and uses its fixed UTC-minute
slot only as the idempotency key. After persisting the sample, or finding that
the slot already contains an equivalent sample, Controller replies:

```json
{"type":"metric_report_ack","report_id":"9fb4e53e8d934b8c88af870266f305c1","ts":"2026-08-23T12:35:02Z"}
```

Agent stores unacknowledged metric reports in a root-owned `0600` atomic state
file, ordered by original `sampled_at`. The queue retains at most 2,048 reports
and drops reports older than 35 days; the count limit is reached first during a
long outage at the normal one-minute cadence. Only the matching head ACK removes
a report. Disconnects, restarts, lost ACKs, and Controller updates therefore
replay the same immutable sample until it is accepted.

## Task Result Callback

### `POST /api/v1/agent/task-results`

Agent-authenticated.

Request:

```json
{
  "task_id": 79,
  "status": "succeeded",
  "result_json": "{\"message\":\"部署已完成\",\"steps\":[...]}",
  "health_report": {"status":"online","agent_build":"20260716000100"}
}
```

Allowed `status` values:

- `succeeded`
- `failed`
- `rollback_failed`

`result_json` must be a JSON object encoded as a string. `health_report` is optional and lets the Agent combine the post-task health refresh with the result callback instead of sending a second WebSocket frame. Controller rejects cross-server results.

After the HTTP callback succeeds, Agent sends `{"type":"task_ack","task_id":79}` on the existing WebSocket. This small acknowledgement contains no duplicate result or health data; it only releases the Controller's in-flight slot so the next queued task can be delivered immediately.

Response:

```json
{ "ok": true }
```

## Task Types

All tasks share `AgentTask` envelope fields. The task-specific contract is the JSON object encoded in `payload_json`.

### `apply_deployment`

The normal panel deployment creates one task per selected server. Its payload contains the ordered plans for WARP preparation, time checking, core config, managed assets, port forwards, local probes, tunnels, optional MTU detection, and optional imported-outbound egress detection. DNS benchmark reconciliation is always included so policy/list revisions and `never` can replace stale local periodic state even when `config_changed=false`. `config_changed` is a Controller comparison hint, not proof of Agent state: for every non-empty config the Agent compares the requested bytes with local `sing-box.json`, returns `reload_strategy=unchanged` for an exact match, and repairs a missing or drifted file even when the hint is false. An empty config with a false hint is retained only as a backward-compatible skip. Empty forwarding, tunnel and asset plans still remove stale state on first reconciliation. After a successful reconciliation, forwarding, tunnel, and SSH-inbound plans whose content differs only by `version` return `unchanged=true` and the deployment records that step as skipped.

Managed assets are references under the nested `config` payload, not file contents:

```json
{
  "config": {
    "config": "sing-box json string",
    "assets": [
      { "kind": "certificate", "id": 7, "revision": "sha256-hex" },
      { "kind": "routing_rule_set", "id": 19, "revision": "sha256-hex" }
    ]
  }
}
```

Core config paths use `oboard-asset://certificate/7/fullchain.pem`,
`oboard-asset://certificate/7/privkey.pem`, and
`oboard-asset://routing-rule-set/19/rules.json` or `rules.srs`. Agent requests only revision files missing
from its cache, stages each revision in a separate directory with directory mode `0700` and file mode `0600`,
and resolves placeholders under `state_dir/managed-assets`. Certificate revision is lowercase hexadecimal
`SHA256(fullchain.pem + NUL + privkey.pem)`; a routing rule-set revision is `SHA256` of its single source JSON
or SRS file. Both downloaded responses and cached files are verified. A corrupt cache entry is downloaded again,
while a mismatched Controller response is rejected. Cleanup handles certificate and `routing_rule_set` assets
independently and removes old or unreferenced revisions only after successful config apply. A failed apply reuses
the staged revision on retry without skipping the required core transition or downloading files again.

Restricted SSH inbounds are carried in the deployment-only `ssh_inbounds` plan. Controller reuses each authorized panel user's proxy password; the panel login password is never used:

```json
{
  "ssh_inbounds": {
    "version": 42,
    "inbounds": [{
      "inbound_id": 31,
      "server_id": 2,
      "name": "tokyo-ssh",
      "listen_ip": "0.0.0.0",
      "address": "203.0.113.20",
      "port": 2222,
      "enabled": true,
      "users": [{
        "user_id": 7,
        "username": "oboard-7",
        "password": "generated-proxy-password",
        "path_id": 12,
        "route_kind": "kernel",
        "route_inbound_tag": "in-31",
        "route_auth_user": "alice__oboard_path_12",
        "enabled": true
      }],
      "policies": {}
    }]
  }
}
```

Agent creates or reuses one persistent Ed25519 host key under `state_dir` with file mode `0600`. A successful or idempotently replayed `ssh_inbounds` step returns its canonical public identity:

```json
{
  "version": 42,
  "unchanged": true,
  "applied": 1,
  "listeners": 1,
  "users": 1,
  "authentication_verified": true,
  "authentication_plan_digest": "<SHA-256 listener and credential identity digest>",
  "authenticated_users": 1,
  "rejected_users": 0,
  "host_public_key": "ssh-ed25519 AAAA...",
  "host_key_fingerprint": "SHA256:..."
}
```

Agent compares passwords in constant time, accepts no client public-key authentication, permits only `direct-tcpip` channels, and applies the existing per-user traffic policy after authentication. The persistent host key is protocol-required server identity rather than a user login credential. Controller validates that the reported fingerprint matches `host_public_key` and derives keyed password deployment digests only from the signed task payload. For a nonempty SSH plan, a result without matching authentication verification is recorded as a failed task and clears the recorded SSH host and password state; older task results cannot overwrite a newer SSH task boundary. Passwords are redacted from public task views and logs; the Agent host private key never enters an Agent task or result.

Before reporting SSH success, including unchanged and focused `apply_core_config` applications, Agent connects to each enabled user's actual local SSH listener and completes password authentication with its persistent host key pinned. No forwarding channel is opened, no payload is billed, and locally registered negative probes do not create credential-rejection audit events. A normal active credential must authenticate; an explicitly rejecting credential or exhausted local quota must reject after the expected password is checked. Missing authorization for an otherwise active credential, stale credentials, missing listeners, host-key mismatch, and handshake failures fail the deployment. Verification has a three-second per-connection deadline and a thirty-second total budget. Failure restores the prior plan, listener and traffic policies without rolling back the independent authorization lease.

The SSH result carries `version`, `authentication_verified`, `authentication_plan_digest`, `authenticated_users`, and `rejected_users`. The digest binds the listener and credential identities (including authorization keys and routes), excludes passwords and quota values, and is generated by the matching model helper in each repository. Controller requires the signed plan's version, identity digest and complete enabled-user count before storing deployment credentials. It derives password digests from the signed task payload, never from Agent-supplied password hashes. Old successful task records without this evidence are unverified and do not expose SSH subscriptions; update Agent first and redeploy to obtain evidence. No schema backfill can manufacture authentication evidence. `credential_status=active` remains an admission-policy value, not an authentication event. Verification proves local SSH authentication or expected policy rejection at deployment time, not public reachability or downstream forwarding availability.

Every enabled SSH credential has `route_kind=kernel` plus a synthetic sing-box `inbound` and branch
`auth_user` identity. A branchless SSH inbound receives one Controller-derived implicit direct-exit branch whose
virtual `path_id` equals the inbound ID; it uses the same kernel route relay and never becomes an Agent direct dial.
Agent resolves and rejects non-public destinations, then calls the current kernel only through
the Unix local API using `CONNECT /routes/relay/tcp`. Headers carry `X-OBoard-Inbound-Tag`,
`X-OBoard-Auth-User`, `X-OBoard-Destination`, and the bounded public
`X-OBoard-Resolved-Addresses` list. The kernel evaluates the normal route table with that identity; Agent never
dials the destination directly when the route API is unavailable or does not select an outbound.

For Shadowrocket-compatible UDP, the restricted runtime intercepts only authenticated `direct-tcpip` requests
for `127.0.0.1:7300` and `[::1]:7300` and serves BadVPN PacketProto/`udpgw` on that SSH channel. It uses the
same branch identity and `CONNECT /routes/relay/udp`; payloads use a two-byte big-endian length frame, while
the destination remains fixed by the authenticated `udpgw` association. Agent does not open TCP port 7300.
All other loopback and private destinations remain prohibited. UDP destinations must be public addresses,
associations are capped at 256 per channel, and relayed UDP payload bytes participate in the same user quota and
connection audit as TCP. Both route endpoints are registered only when the kernel local API listens on Unix;
there is no TCP exposure and no direct fallback.

The Agent returns a single object with `message`, a count `summary`, and a `steps` array. Every step includes `key`, user-facing `label`, `status`, `duration_ms` and optional `result`/`error`. Step status is `succeeded`, `skipped`, `warning`, or `failed`. Managed-asset sync/cleanup, core config, forwarding, tunnel, and SSH-inbound steps are critical. The first critical failure returns immediately without attempting later mutating steps; an idempotent retry skips components that were already committed. Time, WARP, probe, DNS, and MTU failures become warnings so a useful deployment is not reported as wholly failed. The optional `external_egress_probe` runs after `version_state` has persisted the active version; an idempotent deployment replay runs it again because the observation may have changed even when desired state did not.

Controller only emits the top-level task types documented as task headings below. Time checking, WARP preparation, forwarding apply and tunnel apply are deployment steps; Controller also uses the standalone `check_time` task for scheduled and mode-change checks. DNS policy reconciliation is a deployment step, while an operator-requested one-shot test uses `benchmark_dns`.

### `apply_core_config`

Payload:

```json
{
  "config": "sing-box json string",
  "reason": "optional reason",
  "pruned_user_id": 7,
  "assets": [{ "kind": "certificate", "id": 7, "revision": "sha256-hex" }]
}
```

Agent behavior:

- Compare every non-empty requested config with local active state even when a
  deployment supplied `config_changed=false`; repair local absence or drift.
- Return `reload_strategy=unchanged` without validation or reload when the
  requested config exactly matches the active file **and** the running core
  reports the same operational configuration digest. Matching bytes on disk are
  not proof of convergence on their own.
- Validate candidate config with `oboard-sb -check`.
- Reject stale or conflicting task versions before requesting managed assets.
- Request only uncached managed asset revisions, verify certificate and routing
  rule-set content against their SHA-256 revisions, stage by kind/id/revision,
  and resolve only declared placeholders.
- Write candidate config under Agent state dir.
- Atomically replace active config.
- When only the `_oboard` runtime policy block changed, update the local policy
  API and return `reload_strategy=runtime_policy_only` without reloading core.
  This shortcut applies only when the running core already serves the desired
  operational configuration; a runtime policy update must never mask a core that
  is still running older operational state.
- Verify convergence against the running core after every reload or restart. On
  a mismatch, restart the core once and verify again; a core that still reports
  a different operational digest fails the task. A deployment reported as
  succeeded therefore means the running `oboard-sb` has converged, not only that
  the file was written.
- `_oboard.connection_audit.enabled` is emitted only for servers where
  connection auditing is enabled. The core does not allocate audit buckets when
  it is false; disabling the runtime setting clears existing buckets.
- A focused core refresh that would add or change a trusted transparent-forward
  sender or receiver is queued only when the server has a successful full
  deployment with the same trusted-forward fingerprint. Topology, port, or key
  changes must therefore pass through `apply_deployment` first.
- Audit `active_peak` is isolated by device identity (or by the conservative
  legacy source cluster) within one collector. It remains a resource-pressure
  metric and never becomes device count.
- Try hot reload first.
- Fall back to service restart when hot reload is unavailable or fails.
- Roll back to last good config on failure when possible.
- Commit managed asset revision state and delete old/unreferenced revisions only after a successful config apply.

#### Kernel runtime configuration identity

`oboard-sb` advertises `runtime_config_digest_v1` and serves the Agent-only
local endpoint:

```text
GET /runtime/status
```

```json
{
  "state": "running",
  "operational_config_sha256": "sha256-hex",
  "started_at": "2026-09-02T00:00:00Z",
  "pid": 1234,
  "generation": 1,
  "version": "dev",
  "build": "20260903180025",
  "commit": "b6eb4e7fd405"
}
```

It returns identity only; configuration content, credentials, and file paths
never leave the kernel. `operational_config_sha256` is the SHA-256 of the
canonical JSON form of the loaded configuration with the runtime-only members
`_oboard.rate_limits` and `_oboard.connection_audit` removed (an emptied
`_oboard` object is dropped entirely). Agent applies the identical
normalization, so both sides derive the same digest from the same bytes
regardless of key order or formatting. This is the same rule that decides
whether a change is `runtime_policy_only`.

Until the box has started and runtime users have been restored, the endpoint
answers `503` with `{"state":"starting","runtime_security":{...},"pid":1234}`
and no configuration identity. The local API already serves at that point
because Agent pushes the clock, DSCP, authorization, and pool members into a
starting kernel, but a loaded configuration whose inbounds are not listening
yet, or whose start is about to fail, is not a converged kernel. Agent treats
`starting` as `runtime_verification=unavailable`, never as drift or a restart
reason, and keeps polling within its existing verification window: the
watchdog reports `runtime_unreachable`, and `-verify-core-runtime` fails if the
kernel is still starting when the window ends. The runtime security profile is
applied before start, so Agent reads it from either response. Older Agents see
a non-404 error while `/version` still advertises `runtime_config_digest_v1`,
which they also treat as `unavailable`. A started kernel answers `200` with
`"state": "running"`.

Current kernels advertise `runtime_build_identity_v1` and return their build
identity from `/runtime/status`. For older kernels whose runtime-status endpoint
is absent, Agent still reads the running process's JSON `/version` response and
may compare that positive identity with the installed executable. Configuration
verification remains `unsupported`; only a confirmed build mismatch is eligible
for the watchdog's one-time managed recovery.

Agent persists the resulting convergence state in `core-watchdog.json`
(`desired_digest`, `loaded_digest`, `runtime_verified`,
`last_runtime_check_at`, `last_restart_reason`). The core watchdog states are
`running`, `runtime_drift`, `runtime_unreachable`, `recovering`,
`waiting_for_config`, `backoff`, plus the existing `invalid_config`,
`restart_failed`, `crashed_after_restart`, and `recovered` markers. The watchdog
and ordinary deployments share `coreLifecycleMu`, so a watchdog restart and a
deployment can never run at the same time.

### `check_time`

Controller schedules this task for every enrolled online server that has no
time result from the previous 24 hours. An active `check_time` task suppresses
duplicates. Changing a server's correction mode resets its prior telemetry and
queues an immediate forced check when the Agent is reachable.

Payload:

```json
{
  "version": 1783278569000000000,
  "correction_mode": "off",
  "threshold_seconds": 30,
  "ntp_servers": ["time.cloudflare.com", "time.google.com", "ntp.aliyun.com"],
  "force": false
}
```

Correction modes:

- `off`: detect only and disable any persisted logical clock. An absolute raw
  offset of at least 30 seconds is reported as `skewed`.
- `auto`: when the threshold is exceeded, try the allowlisted system time-sync
  command first. If the command is unavailable, fails, or leaves excessive
  skew, enable the logical clock instead.
- `ntp`: never change the host clock; when the threshold is exceeded, enable
  the logical clock directly.

Agent queries exactly three configured NTP sources concurrently with a
five-second batch timeout, requires at least two replies, and uses their median
offset. Controller independently queries the same three sources every minute,
requires the same quorum, and uses its median result to maintain a two-minute
NTP reference cache. Agent control messages include `ts` and `ts_source` only
while that cache is fresh; an unavailable Controller quorum never falls back
to its unverified system clock. A Controller `ts` observed within the previous
two minutes is the Agent fallback when its own NTP quorum is unavailable. When
both references exist, Agent rejects the NTP result if it differs from the
Controller NTP reference by more than five seconds.

Result:

```json
{
  "status": "corrected",
  "correction_mode": "auto",
  "raw_offset_ms": 42000,
  "effective_offset_ms": 0,
  "source": "ntp:time.cloudflare.com,time.google.com,ntp.aliyun.com",
  "checked_at": "2026-07-08T00:00:00Z",
  "system_sync_attempted": true,
  "system_sync_succeeded": false,
  "system_sync_error": "system time sync is unavailable",
  "logical_time_active": true,
  "unsupported_time_paths": ["reality_outbound"]
}
```

`status` is `ok`, `skewed`, `corrected`, `unavailable`, or `config_error`.
`config_error` means the requested correction mode could not be saved before
measurement (for example, atomic rename over a single-file bind mount returns
EBUSY). The standalone task fails, and Controller preserves this status and
`error`, including in deployment step results. No clock measurement or
correction was attempted; zero offset fields are not measurements. Agent keeps
the previous in-memory and persisted mode. Use a writable configuration directory
whose files can be atomically replaced (mount the directory rather than the
individual config file); Agent never falls back to a non-atomic config overwrite.
Retry after correcting the configuration storage. An unchanged mode does not
rewrite the configuration. `unavailable` means the time check could not complete
and is not evidence of clock skew. Only `skewed` indicates a measured excessive
offset. Agent persists an
enabled logical clock in `state_dir/runtime-clock.json` with mode `0600`,
restores it on startup, and sends it to the local kernel after startup and core
recovery. Agent HTTPS/WSS TLS and trusted-forward timestamps use this clock.
The kernel registers it as sing-box's time service so TLS/uTLS, replay windows,
quotas, and connection audit share the effective time. Mieru outbounds are fully covered: the kernel injects the logical clock into
the Mieru fork's wire timestamps and cipher salts. Reality outbounds remain
limited because sing-box stamps part of the ClientHello session ID from the
raw wall clock, and are reported through `unsupported_time_paths` for the
panel warning.

The Agent config's allowlisted `time_sync_command` controls only the `auto`
system-sync attempt. It does not schedule checks. The kernel accepts clock
updates only through `POST /clock/config` on its Unix local API and advertises
the `runtime_clock_v1` capability.

### `apply_vpngate_pool`

Installs the ordered membership of one `vpngate-pool` kernel outbound. The
outbound itself is part of the deployed configuration and carries only
`{"type":"vpngate-pool","tag":"vpngate-<pool_id>","pool_id":<pool_id>}`;
members and the hot-standby count are runtime state delivered by this task, so a
membership change never rewrites `sing-box.json`, never restarts the kernel,
and never allocates a `config_version`.

```json
{
  "pool_id": 3,
  "tag": "vpngate-3",
  "revision": 7,
  "content_digest": "sha256-hex",
  "hot_standby": 1,
  "members": [{
    "member_id": "n42",
    "server": "219.100.37.14",
    "server_port": 443,
    "network": "tcp",
    "cipher": "AES-128-CBC",
    "auth": "SHA1",
    "ca": "-----BEGIN CERTIFICATE-----...",
    "cert": "-----BEGIN CERTIFICATE-----...",
    "key": "-----BEGIN RSA PRIVATE KEY-----...",
    "mtu": 1280
  }]
}
```

`revision` binds `content_digest`, which Controller computes over the hot
standby count and the member list. The Agent and kernel compare that opaque
identity, not their own digest: an older revision is rejected, the same
revision with the same identity is idempotent, and the same revision with a
different identity is a conflict. At most 8 members and `hot_standby` 0-2 are
accepted. The Agent persists the plan to `<state_dir>/vpngate-pools.json`
(mode `0600`) before installing it through the Unix local API, and its
reconciler reinstalls a persisted plan whenever the kernel reports a different
revision for a loaded pool (kernel restart, or a deployment that only now added
the outbound). When the kernel has not loaded the pool yet the task still
succeeds with `installed=false`.

outbound stays in the configuration and refuses every connection. A pool never
falls back to `direct` or any other outbound; Controller config validation and
the kernel both reject a `detour` on a `vpngate-pool`.

Paths with the same source, target, tunnel service port, and target service port carry the same tunnel ID and one local forward. The target Agent creates the locked `oboard_tunnel` account, installs only the derived public key with a per-port `permitopen` restriction, and starts an isolated OBoard-owned sshd executed through an `oboard-sshd` symlink to the host sshd binary, so the listener, argv[0], and the sshd proctitle all identify the daemon as OBoard-owned; on OpenSSH 9.8+ hosts the per-connection re-exec binaries are likewise redirected through `oboard-sshd-session` / `oboard-sshd-auth` symlinks via the `SshdSessionPath` / `SshdAuthPath` directives when the host sshd reports them. After stopping only PID records that still match the recorded command and process start token, the Agent requires the requested port to be free on every local IPv4/IPv6 address. It never reuses a system or external sshd, including one that returns an SSH banner; any external listener fails the tunnel step. The source uses the derived private key with password authentication disabled and verifies the local forward before success. Managed keys are redacted from panel APIs.
- `wireguard`: Linux only. Proxy paths with the same source, target, and keepalive reuse one managed pair even when they carry different shared SS2022 or explicit inbound ports. The Agent installs `wireguard-tools` through a supported package manager when `wg`/`wg-quick` are missing, then applies the projected endpoint. Agent payloads contain the required private/public key fields; path records and panel responses do not.

Controller derives shared tunnel credentials from persistent per-server chain
secrets and the tunnel reuse key. Removing the path that happened to be created
first therefore does not rotate a tunnel that remains referenced by another
path. `DerivedTunnelsFromProxyPaths` de-duplicates shared IDs before building
each server's `TunnelPlan`.

### Deployment step: `warp_requests`

Payload is `WARPRequestPlan`:

```json
{
  "version": 1783278569,
  "server_id": 3,
  "profile_id": 5,
  "name": "warp-v6",
  "ip_stack": "ipv6_only",
  "mtu": 1280,
  "dns_strategy": "ipv6_only"
}
```

Agent's default `warp_command=auto` mode registers a Cloudflare WireGuard device
directly and has no `wgcf` dependency. When the signed core config contains one
explicit interface or source-prefix binding for a pending WARP profile, Agent
uses a local address from that binding for registration and binds the Linux
socket to the owning interface. Conflicting bindings fail before registration
instead of selecting one nondeterministically. The legacy external `wgcf` flow
rejects a bound registration because it cannot enforce that socket route.

The WARP WireGuard tunnel MTU is fixed at 1280 (Cloudflare standard); the Agent
clamps any larger requested value and Controller never seeds the request from
the server's main-network `mtu_value`, because oversized encrypted datagrams get
fragmented and dropped on typical paths, stalling page loads while small control
packets still pass. A cleaned absolute path whose basename is `wgcf` enables the
legacy command flow. `warp_command=none` disables automatic WARP request. Each
report is returned in the parent deployment's `steps` array and persisted by
Controller from the `task-results` callback.

For rule-specific WARP endpoints, Controller derives the outer peer DNS family
from the selected interface inventory or source prefix. Agent preserves that
endpoint-specific resolver while replacing pending placeholders, so an IPv6-only
HE tunnel never inherits the server's default IPv4 WARP peer resolution.

For an explicit `dns_strategy`, the managed WireGuard endpoint uses
`domain_resolver.server=bootstrap-primary`. For `auto` or an empty strategy, the
Agent omits the endpoint resolver and uses the Controller-generated route default.

### `update_agent`

### `apply_stealth`

Payload:

```json
{
  "enable": true
}
```

Controller queues this admin-only task when the per-server security-process
switch changes on an enrolled, online server whose Agent advertises the
`stealth_v1` capability. `enable=true` switches the installation into the
hidden layout: the Agent generates a random identity (installation directory,
binary, service, config, state, log, and socket names), copies the binaries
into the randomly named installation directory beside the current one,
migrates every state file into AES-256-GCM envelopes under HMAC-derived
physical names, writes an encrypted config plus key file, installs the two
renamed service units, restarts the kernel onto its new unit, and disables the
old units. `enable=false` reverses the switch and restores the original
standard layout recorded at enable time.

The switch never destroys the old layout before the new one runs: files are
copied, the new config is verified by loading it back, and the old units are
only disabled. The Agent reports the result first; after `task_ack` it stops
the old unit and starts the new one through a transient one-shot unit. The
process that starts after the switch removes the leftover layout once and
drops the record from its config. The task requires root and a managed service
restart (`restart_command` must not be `none`).

While stealth is active the Agent reports `stealth_active_v1` in
`kernel_capabilities`; `stealth_v1` is advertised whenever the binary supports
the task. In stealth mode `update_agent_config` rejects changes to
`state_dir`, `core_binary`, and `core_service`, and always rejects
`agent_service`, `core_socket`, and `stealth` fields: the layout is managed
exclusively by `apply_stealth`. Shell-driven updates and uninstalls are not
supported on a stealth installation; use the panel (`update_agent` /
`uninstall_agent`), which preserves the generated names across every update.

Result fields:

```json

  "stealth_enabled": true,
  "agent_service": "xk29dm3qpa",
  "core_service": "p7b2nfw9rk",
  "restart": "after_result_acknowledged"

```

### `POST /api/v1/agent/traffic-reports`

Agent-authenticated. This is the current `/api/v1` traffic contract. Delta
`items` payloads and a parallel `protocol_version` field are rejected. Kernel
`GET /traffic/snapshot` and Agent-native SSH snapshots include a per-counter
`counter_epoch`. Agent derives `stream_id` from `source` plus the snapshot key
and a deterministic `report_id` from the range. Controller computes the billed
delta, validates continuity against `traffic_counter_streams`, and returns
`stream_checkpoints` plus `accepted_reports` (`accepted`, `duplicate`,
`covered`, `checkpoint_gap`, `checkpoint_overlap`, `epoch_conflict`, `rejected`).
A lost HTTP ACK retries the same range without double billing. Missing or corrupt
`traffic-state.json` must reconcile against Controller checkpoints instead of
billing `0 → current`. Same-epoch counter regression is fail-closed. Kernels
advertise `traffic_ledger`. ACK payloads include `counter_epoch` and are ignored
on mismatch.

```json
{
  "agent_instance_id": "ce_...",
  "streams": [
    {
      "source": "core",
      "stream_id": "ts_...",
      "counter_epoch": "ce_...",
      "period_key": "2026-08-01",
      "user_id": 1,
      "inbound_id": 1,
      "current_upload_bytes": 1500,
      "current_download_bytes": 4800
    }
  ],
  "reports": [
    {
      "report_id": "tr_...",
      "source": "core",
      "stream_id": "ts_...",
      "counter_epoch": "ce_...",
      "period_key": "2026-08-01",
      "user_id": 1,
      "inbound_id": 1,
      "from_upload_bytes": 1000,
      "to_upload_bytes": 1500,
      "from_download_bytes": 4000,
      "to_download_bytes": 4800
    }
  ]
}
```

Controller verifies:

- no more than 1000 streams and 500 reports are included;
- every report has a stable `report_id` for idempotent accounting, and duplicate
  checkpoint ranges are rejected even when the ID differs;
- byte counters are non-negative;
- a normal inbound belongs to the authenticated server, or a transparent-path
  report names the root inbound and a path whose derived processing server is
  the authenticated server;
- transparent-path reports include a positive `path_id`; the forwarding source
  and downstream shared-link servers cannot report those bytes;
- user is active;
- user is allowed on that inbound.

Ownership failures stay request-level: a report naming another server's inbound
or proxy path, and a user that is not authorized on the inbound, return `403`
for the whole request. Controller cannot tell a removed binding apart from a
claim for access the user never had, so that boundary is never downgraded.

Reports whose accounting subject no longer exists are terminal for that single
report instead of failing the batch. Controller answers `200` and returns the
report with `status=rejected` and a `reason` of `user_deleted`, `user_inactive`,
`inbound_deleted`, `inbound_disabled`, or `path_removed`. Those IDs are not
listed in `accepted_report_ids`, and the bytes are never billed. Agent deletes
the pending report on a terminal reason without entering counter recovery,
because local counters remain consistent. Stream observations whose user is
gone are skipped rather than failing the accounting batch they travel with.

The response returns `stream_checkpoints`, `accepted_reports`, and
`accepted_report_ids`, plus runtime policies only for users whose first
authentication/decryption point is that server. Downstream shared
SS/SSH/WireGuard nodes receive no end-user quota lease and do not report the
same bytes again.

Agent keeps each uncertain report batch durable and unchanged until its ID is
accepted. For every accepted ID it persists the corresponding cumulative
counter checkpoint, then sends that checkpoint to core and Agent-native SSH
before applying the returned baseline. This ordering prevents accepted bytes
from being counted both in `used_baseline_bytes` and in local cumulative
counters. Checkpoints are Agent-local state and are not additional fields on
this Controller request.

Runtime policies carry `lease_bytes`, `reset_lease_bytes`, and
`lease_enforced`. For a limited user Controller always sets
`lease_enforced=true`. Effective cap is `used_baseline_bytes + max(lease_bytes, 0)`,
so a zero remaining lease rejects new billable traffic instead of falling back
to the global quota. They also carry `reset_mode`, `reset_day`, `reset_anchor`,
and `previous_period_key`. `reset_anchor` is an RFC3339Nano timestamp used by
`anniversary_month` and `never`; `previous_period_key` tells Agent/core that a
Controller-side reset-policy migration carried the old period into the current
period. Agent and core retain local unreported counters across that transition,
while an ordinary period rollover starts fresh local counters. A delayed report
using an old key is resolved through Controller's bounded transition chain and
is accounted in the migrated target period.

States with the same `user_id` share one quota inside core or
inside the SSH manager. If both runtimes serve the same user on one Agent, the
Agent partitions the server lease between them; the shares sum to the
Controller allocation. Quota or local lease exhaustion always closes admitted
connections and rejects new authentication. There is no enforcement-mode field.

```json
	  "collection_started_at": "2026-07-18T03:59:00Z",
	  "collection_ended_at": "2026-07-18T04:00:20Z",
      "started_at": "2026-07-18T04:00:00Z",
      "ended_at": "2026-07-18T04:00:20Z"
    }
  ]
}
```

The payload contains metadata summaries only, never connection payloads.
Device/epoch identity, byte totals, payload timestamps, duration histograms,
probe classification, and `presence_sequence` let Controller distinguish a
bound device, meaningful business activity, whole-node tests, and incomplete
bounded collection. `closed_count` equals the sum of the four duration buckets.
Coverage metadata identifies the collection generation/window, bucket capacity,
and buckets dropped after capacity was reached; it is repeated on each durable
item so an unacknowledged batch remains self-contained. The Controller validates
the source IP, counters, coverage bounds and timestamps, active user, authorized
inbound, and transparent-path accounting location. `report_id` is stable and
insertion is idempotent. The response returns
`accepted_report_ids`; the Agent keeps at most 200 items in one delivery batch.

A single malformed item does not poison the batch. Data-shape failures are
terminal for that one report: Controller answers `200`, lists the report under
`discarded_reports` with a stable machine-readable `reason`, and repeats its ID
in `accepted_report_ids` so an Agent that does not read the new field still
drops the pending record.

```json
{
  "ok": true,
  "accepted_report_ids": ["agent-a-connection-1", "agent-a-connection-2"],
  "discarded_reports": [
    { "report_id": "agent-a-connection-2", "reason": "invalid_payload_window" }
  ]
}
```

Reason codes are `invalid_identity`, `invalid_device_identity`,
`invalid_source_ip`, `invalid_source_geo_code`, `invalid_network`,
`invalid_destination`, `invalid_destination_port`, `invalid_counters`,
`invalid_probe_state`, `invalid_collection_coverage`, `empty_report`,
`invalid_started_at`, `invalid_ended_at`, `time_outside_accepted_range`,
`invalid_collection_started_at`, `invalid_collection_ended_at`,
`event_outside_collection_window`, `invalid_payload_window`,
`inconsistent_payload_coverage`, `missing_inbound`, and `invalid_path_id`.

The whole request still fails when the envelope itself is unusable or a
security boundary is crossed: a missing or oversized `report_id` returns `400`,
and a report about another server's inbound or proxy path returns `403`.

Kernel drains guarantee
`collection_started_at <= started_at <= payload_first_at <= payload_last_at <=
ended_at <= collection_ended_at` for every emitted item. A connection that
outlives a drain keeps recording payload into the window that just reset, so
the window end always follows the last payload; the logical clock may step
backwards, and the drain collapses the window rather than emitting an inverted
one.

Collection is opt-in per server and defaults off. While off, Agent does not
poll the core drain endpoint, does not create `connection-audit-state.json`,
and Agent-native SSH does not allocate aggregation buckets. Core collection is
also disabled and holds no audit buckets. When enabled, both core and SSH use
bounded in-memory aggregation; Agent durably stores only an unacknowledged
batch and Controller retains accepted details for 30 days.

Kernel version output must advertise `connection_presence_v1` before Agent
drains `POST /connections/presence/drain`. Missing capability fails the
presence collector instead of silently presenting stale online-device data.
Device `credential_status=reject_new` is applied at authentication time. For
Agent-native SSH, a credential-status-only desired-state change updates the
live authenticator without rebuilding the listener or disconnecting already
authenticated sessions; new authentication is rejected immediately.

## Install and Update Script Endpoints

These endpoints are intentionally outside `/api/v1` and are used by shell install/update commands.

### `GET /install/agent.sh`

The script embeds the Controller URL that served it. Panel-generated commands
therefore only expose the operation and, for first install, the one-time token:

```bash
curl -fsSL 'http://controller:2787/install/agent.sh' | OBOARD_ENROLL_TOKEN='...' OBOARD_INSTALL_BBR=1 OBOARD_INSTALL_TCP_TUNING=0 sh
curl -fsSL 'http://controller:2787/install/agent.sh' | sh -s -- update
curl -fsSL 'http://controller:2787/install/agent.sh' | sh -s -- uninstall
```

The first positional argument or `OBOARD_ACTION` can select:

- `install`
- `update`
- `uninstall`

Important environment variables:

- `OBOARD_CONTROLLER_URL`: optional Controller base URL override.
- `OBOARD_ENROLL_TOKEN`: one-time enrollment token for install.
- `OBOARD_INSTALL_BBR`: `1` enables fixed `BBR + fq` setup during first install; `0` skips it.
- `OBOARD_INSTALL_TCP_TUNING`: `1` applies the fixed TCP tuning set during first install; `0` skips it.
- `OBOARD_AGENT_CONFIG`: defaults to `/etc/oboard-agent/config.json`.
- `OBOARD_AGENT_STATE`: defaults to `/var/lib/oboard-agent`.
- `OBOARD_INSTALL_DIR` or `INSTALL_DIR`: optional normalized absolute binary directory; defaults to `/opt/oboard`.
- `OBOARD_ALLOW_PANEL_UPDATE`: defaults to `1` for the Controller-hosted script.
- `OBOARD_UPDATE_SOURCE`: defaults to `panel`; advanced callers may override it.

The script installs both `oboard-agent` and `oboard-sb` and writes systemd or OpenRC services depending on the host. Fresh interactive installs ask for the binary directory through `/dev/tty`; the choice is stored in `/etc/oboard-agent/install.env` with mode `0600`, and update, uninstall, and self-update operations reuse it. When `OBOARD_INSTALL_BBR=1`, first install also enables the existing kernel's `tcp_bbr` support with `fq` and writes `/etc/sysctl.d/99-oboard-bbr.conf` using mode `0600`. The installer never downloads a BBR script, replaces the kernel, or reboots, and update/uninstall paths do not run the BBR setup.

When `OBOARD_INSTALL_TCP_TUNING=1`, first install also applies a fixed TCP tuning set: file descriptor limit, TCP/UDP buffer sizes (64 MiB maximum), window scaling and SACK options, PMTU probing, RFC 1337 protection, ECN in passive mode, IPv4 and IPv6 forwarding, `route_localnet`, `net.core.default_qdisc = fq`, and `net.ipv4.tcp_congestion_control = bbr`. The list is not configurable. Each key is applied on its own through `/proc/sys`: a key the running kernel does not expose or refuses to change (a restricted container such as some LXC, where `/proc/sys` is read-only) is skipped, reported on stdout, and left out of the persisted file. Only the keys that actually applied are written to `/etc/sysctl.d/99-oboard-tcp.conf` (`/etc/sysctl.d/99-net-params.conf` in security-process mode) with mode `0600`, so a reboot never replays an unsupported key. When nothing applies, the installer keeps going without writing a file. The setup never changes the kernel or reboots, and update/uninstall paths do not run it. It is independent of `OBOARD_INSTALL_BBR`: the tuning set contains `fq` + `bbr` on its own, and both switches write consistent values into their own files.

### `GET /install/agent-self-update.sh`

Used by `update_agent` when source is `panel`. It downloads:

- `/downloads/oboard-agent-linux-amd64` or `/downloads/oboard-agent-linux-arm64`
- `/downloads/oboard-sb-linux-amd64` or `/downloads/oboard-sb-linux-arm64`

The script can delay restarting `oboard-agent` so the current HTTP task result can be posted before process replacement. It reads the persisted install directory before replacing either binary.
Its download helpers use the same three-attempt limit and `curl --continue-at -`, so a transient Controller connection loss keeps the partial file for the next attempt instead of restarting the transfer.

## Protocol Rules

- Unknown task types must fail with `unknown task type`.
- Removed standalone task names are not accepted as aliases; Controller and Agent must be upgraded together before release.
- New task types should be gated by Agent build in Controller before enqueueing.
- Missing optional health fields must not fail enrollment or heartbeat processing.
- Missing OS helper commands must be returned as diagnostic/log method errors, not panic or task crashes.
- `payload_json` and `result_json` are JSON object strings stored in SQLite.
- Sensitive values in diagnostics/log output must be redacted: token, password, private key, secret and related fields.

## Remote Access

Remote Terminal is an Agent PTY relay for human operators. It is not SSH, does
not use TCP/22, and does not occupy the single Agent task slot.

The PTY child is a login-compatible Unix session for the Agent's current
account: passwd shell with `-l`, HOME as cwd, and a reconstructed environment
(`HOME`/`USER`/`LOGNAME`/`SHELL`/`PATH`/`TERM`). Login mode also loads
`/etc/default/locale` or `/etc/locale.conf`, `/etc/environment`, and optional
`/etc/oboard-agent/terminal.env`. It does not inherit `os.Environ()`, Agent
tokens, `OBOARD_*` process variables, or `SSH_*`, and it does not run PAM,
`login -f`, `su -`, or `/etc/ssh/sshrc`. `mode=minimal` skips those files and
`-l` so a broken profile can still open a shell.

Control-channel messages (signed HMAC, 60s prepare TTL):

Interactive timestamp validation uses the fresh Controller reference attached
to the authenticated control frame, then the Agent's persistent logical clock,
and only then the host wall clock. The signed window must be positive, no longer
than 60 seconds, unexpired, and no more than 30 seconds in the future. Controller
signs the envelope in the same NTP-backed time domain when that reference is
available; clock correction does not weaken or widen the replay window.

- `interactive_prepare` — Agent validates signature, server_id, nonce, TTL, and
  the local security gate, then starts a login-compatible PTY and dials
  `/api/v1/agent/interactive/{session_id}` with
  `X-OBoard-Interactive-Proof`. PTY start uses the PTY library session
  (`Setsid`/`Setctty`) and must not also set `Setpgid`. Shell, cwd, and
  environment are resolved on the Agent host: the current Unix account, the
  passwd login shell with `-l` (or `mode=minimal` without profiles), HOME as
  cwd, and a from-zero environment. Controller may send `mode=login|minimal`
  only when the Agent advertises `terminal_login_env_v1`; it must not send
  `shell`, `command`, or `env`. Signature canonical bytes stay the existing
  cols/rows envelope so older Agents keep verifying. Missing `mode` defaults
  to login on Agents that implement this capability.
- `interactive_ready` — Agent → Controller after the PTY is up and the reverse
  WebSocket is connected. Controller cancels the 20s prepare timeout. The Agent
  also writes `{"type":"ready","info":{...}}` on the reverse WebSocket; the
  browser shows connected only after that message. `info` is diagnostic
  identity only (username, uid, gid, home, shell, mode, cwd, term, environment
  file loaded flags) and never includes environment values or terminal bytes.
- `interactive_failed` — Agent → Controller when PTY start, interactive URL
  construction, reverse WebSocket dial, session-limit, local-gate, prepare
  validation, nologin shell, or missing login shell fails. Payload is
  `{session_id, reason, detail?}`. Controller deletes the session, writes
  `{"type":"error","reason":"...","detail":"..."}` to the browser if connected,
  and sends `interactive_close`. `login_shell_disabled` and
  `login_shell_missing` are readable Agent-local failures; `shell_exited`
  closes a session whose login shell has already left.
- `interactive_close` — Agent closes the PTY, signals the process group, and
  waits then SIGKILLs leftovers.
- `remote_exec_cancel` — best-effort cancel of an in-flight `remote_exec` by
  `request_id`.

If the Agent does not connect the reverse WebSocket or send `interactive_ready`
within 20 seconds, Controller closes the session with `reason=prepare_timeout`
so a failed prepare cannot occupy a terminal slot.

The Agent WebSocket reader is decoupled from the single-slot task worker so
prepare/close/cancel/heartbeat continue while a deployment is running.

`remote_exec` and `remote_operation` are ordinary signed Agent tasks. Structured
exec uses `exec.CommandContext` with argv (no shell). Raw shell uses
`/bin/sh -c`. Agent keeps an at-most-once journal under `{state_dir}/remote-exec/`
keyed by `request_id` and payload SHA-256. stdout/stderr are returned on the task
callback and must not be persisted in Controller task history.

Hello/health advertise:

```json
{
  "remote_access": {
    "capabilities": ["remote_terminal_v1", "terminal_login_env_v1", "remote_exec_v1", "remote_access_local_gate_v1"],
    "local_mode": "standard",
    "local_allow": {
      "remote_terminal": false,
      "mcp_remote_operations": false,
      "mcp_structured_exec": false,
      "mcp_raw_shell": false
    }
  }
}
```

Local hard gate is `/etc/oboard-agent/local-security.json` (mode `0600`).
`update_agent_config` cannot modify it. Hardened mode requires the matching local
allow bit; Controller cannot remotely raise a deny to allow or switch Hardened
back to Standard. Use `obag remote-access` on the host as root.

Controller must not enqueue `remote_exec` / `interactive_prepare` to Agents that
do not advertise the matching capability.
